# 全场景开发优先级与验收计划 V1.4

日期：2026-09-14。P0已进入本地开发实现；真实平台接入、商家规则确认和执行外发尚未开展。实现与验证证据见 [全场景 P0 实现说明](FULL_SCENARIO_P0_IMPLEMENTATION_V1_4.md)。

## 优先级依据

全场景矩阵覆盖218个场景。P0为所有场景的识别、规则管理、补证和人工兜底；矩阵中P1/P2/P3标记进一步业务闭环的开发批次。高风险场景可以后置自动化，但风险识别/接人必须在P0进入系统。

排序依据：当前代码复用程度、闭环依赖、可观察的节省操作步骤、风险和单人维护成本。发生频率、当前耗时、错误率和客户预算均未知。禁止以话术条数推断“高频”，禁止把本排序作为已验证商业价值排名。

建议估算：P0为4–6、P1为6–10、P2为5–8个个人专注工作日（按每天约6小时）；是初步工作量假设，不是交期承诺。单人串行约15–24工作日，包含本地实现和测试，不含商家确认、平台审核、真实联调和部署。每阶段完成后重估，避免因套餐窗口承诺全部上线。

## P0：全场景识别与规则底座

| 任务 | 实现范围 | 验收 |
| --- | --- | --- |
| P0.1 场景定义与发布 | 增加稳定ID、别名、适用店铺/平台/SKU、来源坐标、版本、生效期；已有知识发布复用 | 218条可追溯；来源更名不改变既有ID；冲突规则保持草稿 |
| P0.2 案件事实 | 新增多轮事实、来源、可信状态、时间、缺项、客户诉求和多意图 | 已提供数量不重复追问；不同订单不拼接；新风险令旧方案失效 |
| P0.3 决策接口 | 模型仅提建议；风险、事实、规则适用和授权由代码复核 | 未知场景、工具失败、模型格式错均进入可用人工路径 |
| P0.4 角色与审批 | 质量职责；逐单/批量/规则直派分别授权；资金/食安人工边界 | 客服不能冒主管、不同部门不能越权；AI不能授权退款 |

交付：更新实际应用的全场景入口、规则草稿管理、决策接口及测试报告。业务规则未确认的场景只做建议与转人工，不放行自动操作。

## P1：可复用的核查、催办和结果闭环

入选方向：物流停滞/签收未收到、分包裹与错漏发、普通包装异常、缺货替代、退款进度、退货验收、客服催办和客户未回复。矩阵内具体场景有独立批次；进入该批不等于可以自动退款。

| 任务 | 实现范围 | 验收 |
| --- | --- | --- |
| P1.1 案件和任务分离 | 一案件多子任务、主责、协同、依赖和结果合并 | **本地已实现**；仓库完成而财务待处理时不能结案，退回上游会使下游旧回执失效 |
| P1.2 低风险流程包 | 每个场景必要事实、核查任务、回执和客服草稿 | 入选场景均覆盖正常/缺项/升级/重复；少件先查分包裹 |
| P1.3 时效机制 | 时效起点、工作日、提醒、升级、客户等待/挂起恢复 | 48小时不是硬编码统一值；超时任务可恢复且不重复催办 |
| P1.4 回执与重试 | 标准事件、幂等、乱序、超时未知状态与人工核对 | 通知接受不算接单；操作超时不重复补发；回执对象不符拒收 |
| P1.5 客服收尾 | 结果草稿、客户方案确认、退回核实、结案及重新打开 | 客户不回复时挂起；仅记录“已催促”不得当作问题解决 |

P0开始就核查咨询入口、吉客云字段/费用/权限和企业协作通道。外部权限不阻塞本地契约测试，但真实通道是付费集成上线门槛。

## P2：复杂政策、活动与资金方案

活动资格、赠品兑现、差价、退换政策、运费、退款金额分解、开票会员、平台争议与仓库驳单。现有通用工单继续复用；规则必须按商家/平台版本配置。

资金动作先支持方案计算和人工审批记录，与实际资金执行分开；退款原因需符合事实，不能按模板任意改写。食安、伤害、投诉仍由主管和专责人员处理。

验收：政策版本切换不污染历史案件；金额、数量、时效边界有独立期望；客户更换方案重新审批；无真实执行回执不能说“已到账/已换货”。原表已发现换货支持范围、物流24/48小时和金额表述疑点，逐项解决后再发布。

## P3：专项和真实连接器扩展

先按付费客户选择一条真实接入组合：一个咨询平台 → 吉客云只读订单/售后/库存中所需能力 → 一种企业协作工具 → 部门回执 → 客服确认回复。不得用ERP权限代替聊天权限，不能把任意页面抓取当作可靠平台连接器。

品牌参数、资质文件、配方解释、平台专项、器具故障按需求增加。源资料中的质量和活动长尾已归回对应业务域，但其专项自动化可以后置。接口资质、费用、字段映射和版本需在实施时按官方来源再次核实；本计划没有重新开展网络调研。

验收：真实测试咨询接收、店铺/对象关联、事实查询、获权通知、人员接单、业务回执、客户回复各自留证；部署权限、故障恢复、备份、持续支持责任明确。P3联调工作量未知，不承诺具体天数。

## 付费试点与是否继续投入

目标是一家单店限定范围的付费试点，不表示已经成交。售卖范围写清选定场景、咨询入口、连接系统、角色、服务时间、变更次数、验收指标、模型与第三方费用承担。收费结构为接入/规则配置服务加持续使用维护；具体金额需根据工作量、成本和客户预算确认。

先对照客户已正确配置的原系统，记录至少一周实际流程：每单主动操作分钟数、等待部门时长、追问次数、错分派/漏处理、模型/接口成本、每周支持时间。建议按同类案件至少30单进行前后对照（不足时写明样本量和不确定性），建议目标为主动操作时间中位数减少20%；这是拟议验收目标，须由客户确认，不能当作已验证收益。

生产放行底线：评测中不能越权执行，高风险必须接人；源系统结果可追溯；支持人工接管和故障恢复。人工抽样核对关闭案件的真实完成情况，防止只提高系统里的结案率。

月度经济性记录：实收费用 − 模型/API/托管费用 − 支持工时×自行设定的工时成本。缺货询问不能直接当作损失订单，回复速度提升也不直接当作成交收入。若原系统配置即可解决、客户无预算或定制维护不能摊薄，先收缩交付范围。

## 本轮交付验收

- 场景ID唯一、总数218；原表1969阶段行全部有归属，来源哈希前后相同。
- 矩阵每项包含原表定位、输入依据、建议风险/部门/审批/连接器/闭环/批次和待确认项。
- HTML无需后端，包含搜索、业务域/风险/批次过滤、详情及CSV下载；设计内容不写入正在对外演示的应用数据。
- 架构与已实现代码分别说明；未承诺真实模型效果、已获平台权限或可直接自动处理全部场景。

P0.1至P0.5的本地底座已经实现：218条规则草稿、事实检查、多轮重判、角色边界和全量登记基准。下一步是由业务人员填写确认清单，并用自然语言合成改写补强测试；未经确认的规则继续停在人工路径。
